\chapter{taskman --- The Central System Server}

\section{Role}

\texttt{taskman} is the root server process in QSOE.  It is analogous
to QNX's \texttt{procnto}: a single user-space process that
combines the responsibilities of a process manager, memory manager,
path manager, and system service provider.

Because seL4 provides only the bare capability and IPC mechanisms,
\texttt{taskman} is responsible for all higher-level OS policy.

\section{Startup}
\label{sec:taskman-startup}

After sel4runtime hands control to \texttt{main()}, taskman:

\begin{enumerate}
    \item Inspects \texttt{seL4\_BootInfo} to discover available untyped
          memory and initial capabilities.
    \item \textbf{Bootstraps its primary endpoint.}  This step is the
          one piece of taskman that cannot use the QNX-compatible
          \texttt{ChannelCreate} API, because the API itself
          (Chapter~\ref{chap:libqsoe}) is implemented as an IPC to
          taskman --- and no endpoint exists yet to send that IPC to.
          Taskman therefore allocates one Endpoint directly with
          \texttt{seL4\_Untyped\_Retype}, stashes the master capability,
          and inserts an entry for itself into the channel registry
          (\S\ref{sec:registries}) by hand, owner \texttt{pid=1},
          \texttt{chid=1}.  From this point on, every other channel in
          the system is created through the regular API path.
    \item Initializes internal subsystems: memory allocator, process
          table, pathname space, channel and connection registries.
    \item Enters the main loop: \texttt{seL4\_Recv} on the primary
          endpoint, dispatch on the message label, \texttt{seL4\_ReplyRecv}
          to reply and immediately receive the next request.
\end{enumerate}

\section{Process lifecycle}
\label{sec:process-lifecycle}

QSOE's process model is QNX-style: no \texttt{fork()}, only
\texttt{posix\_spawn()} (per CLAUDE.md's architectural decisions).
\texttt{taskman} owns the pid namespace and the master capabilities
for every kernel object backing a process.

\subsection{pid allocator}

pid 1 is reserved for \texttt{taskman} forever.  Child pids start at
2 and are bump-allocated up to \texttt{TM\_MAX\_PROCESSES-1}; freed
pids land on a LIFO free list and are reused before the bump pointer
advances.  No reserved ranges or family bits yet --- v0.5+ can add
them when the system grows multiple service tiers.

\subsection{Spawn (ProcessCreate / posix\_spawn)}

The libqsoe entrypoint is \texttt{ProcessCreate(path)} returning the
new pid, plus a POSIX-shaped wrapper \texttt{posix\_spawn()} that
ignores file\_actions / attr / argv / envp for v0.4.1 (argv/envp on
the child stack lands in v0.4.2).  Wire request label
\texttt{TM\_REQ\_PROCESS\_CREATE} carries the path length in MR0 and
the path bytes in \texttt{ipcbuf->msg[4..]} --- past the four
register-transferred MRs.

Taskman receives the request, looks up the named ELF in the embedded
userland CPIO, allocates a fresh pid, calls the existing
\texttt{tm\_spawn} sequence (Chapter 3.4) under the new pid, and
replies with the pid.  No argv/envp delivery yet --- the child gets
just \texttt{a0 = pid} as before.

\subsection{Termination (ProcessTerminate / exit / \_exit)}

Two paths share the same handler:

\begin{itemize}
    \item \textbf{Self}: the child calls \texttt{exit(status)}, which
          (in v0.4.1) is a direct alias for \texttt{\_exit(status)},
          which sends \texttt{TM\_REQ\_PROCESS\_TERMINATE} with
          \texttt{pid=0}, \texttt{status=N} to taskman.  The crt0
          falls through to \texttt{\_exit(main's return value)} so a
          plain \texttt{return 0;} from \texttt{main()} cleanly
          terminates the process.
    \item \textbf{External}: another process calls
          \texttt{ProcessTerminate(target\_pid, status)}.  Same wire
          label; taskman uses the badge to authorise the request.
\end{itemize}

\texttt{tm\_process\_terminate} revokes the target's master caps in
order: worker thread TCBs and join Notifications, owned channels,
client-side connection records, main TCB, VSpace, CNode, the
workers' L0/L1 page tables, and finally the per-child untyped
budget.  Then it frees the pid.

\textbf{No-reply dispatch} for self-terminate: revoking the caller's
TCB inside the handler means the caller's thread is gone before
taskman would normally call Reply.  The dispatch loop honours an
\texttt{out\_no\_reply} flag set by the handler and switches from
\texttt{seL4\_ReplyRecv} to \texttt{seL4\_Recv} for the next
iteration --- otherwise it'd block forever waiting for a reply target
that no longer exists.

\subsection{Cap-leak hygiene}

Taskman maintains a slot free list
(\texttt{s\_slot\_free\_list[256]}).  Every \texttt{CNode\_Delete} on
a taskman-allocated slot pushes the slot back to the list; every
\texttt{taskman\_alloc\_and\_retype()} pops from the list before
bumping \texttt{s\_next\_slot}.  The cap-leak smoke test verifies
this: 100 cycles of \texttt{ChannelCreate} + \texttt{ChannelDestroy}
yield \texttt{delta = 0} in taskman's bump pointer.

Slot reuse within a child's own CSpace (\texttt{p->next\_slot}) is
not yet implemented in v0.4.1 --- the cost is purely CSpace room in
the child, not kernel memory.  v0.5 generalises.

\section{Untyped budget per process}
\label{sec:untyped-budget}

Each spawned process receives an untyped capability of fixed size
($2^{18}$ bytes = 256 KiB in v0.4.1) at boot, copied into well-known
CSpace slot \texttt{QSOE\_CAP\_OWN\_UNTYPED} (= 2).  The cap lives in
the child's CSpace; the master copy stays in taskman's CSpace,
recorded in \texttt{tm\_process\_t.untyped\_budget} so
\texttt{tm\_process\_terminate} can revoke + delete it cleanly.

In v0.4.1 the budget is \emph{established} but not yet consumed:
libqsoe's \texttt{ChannelCreate} still goes through taskman for the
retype.  v0.5 will let the child do that retype locally from its own
budget, removing one round-trip per channel.  This decentralises
allocation but doesn't change the security model --- taskman still
owns the master caps via the parent / child untyped derivation tree
and can Revoke at ProcessTerminate time.

The budget size is currently a fixed compile-time constant.  A v0.4.2
\texttt{posix\_spawnattr} extension will let callers ask for a larger
budget at spawn time.

\section{SMP boot}
\label{sec:smp-boot}

QSOE is built for SMP from v0.3.4 onward.  The reference target is
\textbf{4 harts on qemu-riscv-virt}; the SiFive Unmatched (5 harts:
4$\times$U74 + 1$\times$S7) and the SpaceMit K3 (8 cores) are
configuration-time changes to \texttt{CONFIG\_MAX\_NUM\_NODES}.

The seL4 kernel is built with \texttt{KernelMaxNumNodes=N},
\texttt{KernelEnableSMPSupport=ON} (auto-enabled by sel4test's
\texttt{settings.cmake} when \texttt{SMP=TRUE}).  The elfloader
(\texttt{core/kernel/startup/}) is built with our own Makefile rules,
which emit a tiny \texttt{autoconf.h} containing the matching
\texttt{CONFIG\_MAX\_NUM\_NODES} and \texttt{CONFIG\_ENABLE\_SMP\_SUPPORT}
defines; the elfloader's secondary-hart bringup code paths
(\texttt{boot.c}, \texttt{crt0.S}) compile in when those defines are
present.

At boot, hart 0 runs the elfloader's \texttt{run\_elfloader} sequence
to completion, then secondary harts are released via the OpenSBI HSM
extension.  Each secondary enters \texttt{secondary\_entry}, joins a
ready-flag barrier, and enables paging before jumping into the kernel.
The kernel then constructs its per-CPU state and starts the rootserver
(taskman) on hart 0.

In v0.3.4 taskman remains a single-threaded server pinned to hart 0
--- the v0.3.3 transcript replays unchanged.  Secondary harts are
present and idle; they only come alive when user threads are pinned
to them via \texttt{seL4\_TCB\_SetAffinity}.  v0.4 layers the QNX
\texttt{Thread*} API on top, exposing affinity through
\texttt{\_thread\_attr.runmask}.  Multi-threading taskman itself is
deferred to v0.5+, when the first resource manager arrives and the
single-server dispatch bottleneck becomes meaningful.

The invocation-label enum shifts under SMP: \texttt{TCBSetAffinity}
is inserted at slot 15, pushing every later label up by one.
QSOE re-derives the \texttt{INV\_*} constants in
\texttt{userland/taskman/sel4\_types.h} from the kernel's generated
\texttt{invocation.h} after every kernel rebuild.

\section{Message-passing model}

All interaction with \texttt{taskman} follows the QNX
Send/Receive/Reply pattern:

\begin{enumerate}
    \item A client calls \texttt{MsgSend()} (maps to \texttt{seL4\_Call}),
          which blocks the sender.
    \item \texttt{taskman} calls \texttt{MsgReceive()} (maps to
          \texttt{seL4\_Recv}) to dequeue the next message.
    \item \texttt{taskman} processes the request and calls
          \texttt{MsgReply()} (maps to \texttt{seL4\_Reply}) to unblock
          the sender with the result.
\end{enumerate}

Asynchronous notifications (pulses) use \texttt{MsgSendPulse()},
mapped to seL4 Notification objects, for interrupt delivery and
lightweight signaling.

\section{Channel and connection registries}
\label{sec:registries}

For \texttt{ConnectAttach} to translate a \texttt{(pid, chid)} pair into
a usable capability, some component must hold the authoritative mapping
from those identifiers to the underlying seL4 Endpoint object.  seL4
itself has no global namespace --- every capability lives in some
process's CSpace.  In QSOE, that authority is \texttt{taskman}.  Two
small tables make this concrete:

\begin{lstlisting}[language=C]
struct tm_channel {
    seL4_CPtr master;      /* master Endpoint cap in taskman's CNode */
    pid_t    owner_pid;
    int      owner_chid;   /* libqsoe-picked, process-local */
    unsigned flags;
};

struct tm_connection {
    struct tm_channel *channel;
    seL4_Word badge;
    pid_t     client_pid;
    seL4_CPtr client_slot; /* slot the client received */
};
\end{lstlisting}

For early QSOE versions both tables are flat arrays with linear scan,
sized at compile time (currently 64 channels, 256 connections).  They
grow to hash tables when measurement says it matters.

\subsection*{Key invariant}

\texttt{taskman} holds \emph{exactly one} master capability per
channel.  Every other capability to that endpoint anywhere in the system
--- the server's recv-side copy, every client's badged Send copy --- is
a derived descendant of that master.  Consequently:

\begin{itemize}
    \item \texttt{seL4\_CNode\_Revoke(master)} atomically tears down
          every reference to the channel in one call.  This is what
          makes \texttt{ChannelDestroy} and process-exit cleanup
          tractable.
    \item No process can resurrect or forge a connection to a destroyed
          channel: the underlying Endpoint object is gone.
    \item A misbehaving server cannot starve clients of cleanup by
          refusing to participate, because clean-up is initiated by
          \texttt{taskman} from its own master capability.
\end{itemize}

\section{Cleanup on process exit}
\label{sec:exit-cleanup}

When a process exits --- either through \texttt{ProcessTerminate} or by
fault --- \texttt{taskman} reclaims every resource that process owned
or held connections to:

\begin{enumerate}
    \item Walk the channel registry for entries with
          \texttt{owner\_pid == exited\_pid}.  For each, invoke
          \texttt{seL4\_CNode\_Revoke} on the master capability (which
          cascades to all clients) followed by \texttt{Delete}, then
          remove the registry row.
    \item Walk the connection ledger for entries with
          \texttt{client\_pid == exited\_pid}.  For each, delete the
          client-side Send capability and remove the row.
    \item Free the process's TCB, VSpace, CSpace, and any other
          per-process objects --- detailed in the future \emph{Process
          manager} section of this chapter.
\end{enumerate}

The point of describing this here rather than under \texttt{taskman}'s
process-manager service is that the invariant in \S\ref{sec:registries}
is what makes step~1 a single \texttt{Revoke} per channel rather than a
client-by-client search.

\section{Generated headers from the kernel build}

Invocation method labels and syscall numbers are kernel ABI surface,
gated on \texttt{CONFIG\_KERNEL\_MCS}, \texttt{CONFIG\_ENABLE\_SMP\_SUPPORT},
and other compile-time options.  v0.4.3 stopped hand-counting them in
\texttt{userland/taskman/sel4\_types.h} and instead pulls the four
kernel-generated headers via \texttt{scripts/placement.txt}:

\begin{itemize}
    \item \texttt{api/invocation.h} --- the generic
          \texttt{enum invocation\_label} (\texttt{UntypedRetype},
          \texttt{TCBConfigure}, \texttt{CNodeRevoke}, etc.).
    \item \texttt{arch/api/invocation.h} --- the arch-specific
          \texttt{arch\_invocation\_label} (\texttt{RISCVPageTableMap},
          \texttt{RISCVASIDPoolAssign}, etc.).
    \item \texttt{arch/api/sel4\_invocation.h} --- glues the two
          enums together so the arch labels start at
          \texttt{nInvocationLabels}.
    \item \texttt{arch/api/syscall.h} --- the
          \texttt{enum syscall} (\texttt{SysCall}, \texttt{SysReplyRecv},
          etc.) and \texttt{SYSCALL\_*} macros for assembly.
\end{itemize}

These live under \texttt{core/kernel/sel4\_gen/} and are refreshed
from the kernel build whenever a config option changes.  Taskman's
\texttt{INV\_*} and \texttt{SYS\_*} macros are now thin aliases for
the upstream enum members --- a kernel reconfigure no longer requires
a manual recount and re-edit of \texttt{sel4\_types.h}.

\section{Multi-server IPC}

QSOE is built on the premise that every system service after taskman
is a userland process.  v0.4.3 demonstrates the full path end-to-end:
the \texttt{hello} binary, previously a \texttt{print-and-exit} demo,
now does a complete server loop:

\begin{enumerate}
    \item \texttt{ChannelCreate(0)} --- gets \texttt{chid=1} (the
          first FD-namespace chid).
    \item \texttt{MsgReceive} / \texttt{MsgReply} three times.
    \item \texttt{ChannelDestroy(1)} and exit.
\end{enumerate}

The tester, on receiving \texttt{hello}'s pid back from
\texttt{posix\_spawn}, then:

\begin{enumerate}
    \item \texttt{ConnectAttach(ND\_LOCAL\_NODE, hello\_pid, 1, ...)}
          --- with retry, since hello may not yet have reached
          \texttt{ChannelCreate} when the first attempt fires.
    \item \texttt{ConnectServerInfo(0, hcoid, \&si)} --- confirms
          \texttt{si.pid == hello\_pid} and \texttt{si.chid == 1}.
    \item Three \texttt{MsgSend} round-trips with payload+1 echo.
    \item \texttt{ConnectDetach}.
\end{enumerate}

scoids remain in a single global namespace (the per-channel
namespacing QNX uses is a QNX-faithfulness refinement deferred until
the 28-bit endpoint-badge space gets uncomfortable, which won't
happen for the foreseeable future).
